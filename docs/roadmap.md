- [x] **Two correctness bugs from an external code review, both verified against the actual code before fixing:**
  - **Template edits could retroactively rewrite history.** `isDayCompliant` always re-resolved *today's* live `weekPlan`/template to judge a past day's completeness — so editing a template's exercise list, or permanently reassigning a weekday to a different template, could silently flip an already-completed past day to incomplete (and drop your streak/consistency) with no warning. Fixed by having each session record the `templateId` and a frozen `templateSnapshot` of the template's exercises at the moment it's created; compliance and rendering for a day now prefer what that day actually recorded over today's live plan. Sessions logged before this fix have neither field and fall back to the old (re-resolve-live) behavior — there's no way to recover history that was never captured. One follow-up bug this surfaced in testing: a same-day re-swap (e.g. swap to cardio, log something, realize you meant a lift day and swap again) left the already-created session's snapshot stale, so the UI got stuck showing the pre-swap type. Fixed by having `confirmSwap` re-baseline an existing session's recorded assignment — a swap is a deliberate, explicit correction to *that specific day* and should take effect immediately, unlike an unrelated template-content edit made later, which should not.
  - **Bodyweight exercises could never register a PR.** `countRecentPRs` only tracked weight-based PRs and exited immediately for any set with no weight logged — meaning Push-Up, Plank, and any bodyweight/timed exercise contributed zero to the Strength attribute no matter how much they improved, since half the default templates are bodyweight work. Fixed: a session with any weight logged is judged as a loaded performance (weight is the PR axis); one with none is judged as bodyweight/timed (reps or seconds, same field, is the axis instead) — decided per session, not fixed per exercise name. The runtime "New PR!" toast had the identical bug in a separate, simpler check and got the same fix, so it now agrees with the Strength attribute on what counts. Catalog entries gained a `bestReps` field alongside `bestWeight` (additive, no migration needed).
- [x] **Progression suggestions used the wrong signal.** `suggestProgression`'s "did you hit target" check was based on whichever set happened to be typed *last* that session, not the worst one — `10/10/8` and `8/10/12` (last set exceeding target while an earlier one missed it) could both misread as a hit. Fixed at the source: the catalog now records the *minimum* reps across all sets that session (so "hit target" correctly means every set met it) and the *maximum* weight used (the weight actually being worked, not whichever set was filled last). No change to `suggestProgression` itself was needed — the fix is entirely in what gets fed into it.
- [x] **Five more findings from a second code review, verified individually:**
  - **Streak-milestone XP could silently fail to save.** The bonus is awarded from inside a `setTimeout` fired 900ms after the triggering action's own synchronous save already ran; `awardXp()` only mutated `state.xp` in memory. Closing the tab right after a milestone (a very plausible moment to do exactly that) lost up to 400 XP on reload with no indication anything was wrong. Fixed by having `awardXp` persist whenever it actually adds XP — closes the whole bug class rather than patching each call site.
  - **Template Sets/Target fields could be set to 0.** Floored at `Math.max(0, ...)` instead of 1; `allSetsComplete(sets, 0)` trivially returns true with nothing logged, so a stray 0 could mark an exercise — and via the workout-complete check, the whole day — complete with no data, inflating streak/consistency by accident. Floored at 1, matching the custom-exercise modal's existing behavior.
  - **A blank readiness field scored as an extreme, not "no data."** Blank Resting HR coerced to 0, which scored as the *best possible* reading (nudging toward PUSH); blank Sleep Score also coerced to 0, which scored as the *worst possible* reading — the same missing input treated as great news for one field and terrible news for the other, purely by accident of `Number("") || 0`. Fixed so a blank field contributes nothing to the score in either direction.
  - **Import had no confirmation.** Picking a file immediately replaced all current state — given the entire reason this app was rebuilt was losing data, a one-line `confirm()` before overwriting was cheap, obvious insurance.
  - **The AI digest ignored this-week swaps.** Its "Current plan" section read `state.weekPlan` directly instead of resolving through `weekOverrides`, so a swapped day was reported to an AI reviewer as if the swap never happened. Now resolves the actual current week's plan and marks swapped days.
  - Explicitly not done this round: mid-typing focus loss on rapid cross-set edits (real, but needs a focus-preservation mechanism across re-renders — bigger than a one-line fix), an export-reminder banner, memoizing `computeStreakInfo` per render, `inputmode` consistency on non-set-row number inputs, and pruning the unused `session.type` field — all lower value or premature without real usage data yet.
- [x] **Plateau detection + a structured plan-change import**, closing the loop the AI digest started:
  - The digest now includes a "Plateaued exercises" section (`detectPlateaus` — no net progress across the last 3 logged sessions, weight-axis or reps/seconds-axis per exercise same as PR detection) and asks the AI to name concrete changes rather than general advice.
  - If the AI has concrete changes, the digest asks for them as a fenced `json` code block in a documented shape (which templates to edit, full exercise lists, weekday reassignments). Settings → **Import Plan Changes** lets you paste the whole response back in — the JSON is found and extracted automatically. Deliberately *not* a live API loop (same reasoning as the digest itself: no safe place to hold credentials in a static file, and a human should stay the one deciding what changes in their own program, not have an AI silently rewrite it). Preview-before-apply is non-negotiable: pasting shows a plain-language diff ("Pull-Up: 4×8 → 4×10", "Fri: Upper Body Accessory → Cardio") and nothing touches the plan until Apply is tapped. Scoped to only what Settings' own editor already allows changing (a template's exercises, weekday→template assignment) — no new templates, no touching sessions/history/XP/readiness.
  - Surfaced and fixed a real, pre-existing bug while building this: `Store` cached its own copy of state, set once at load and never updated again, so any code path that *reassigned* `state` to a new object (JSON import, this new plan-change apply) rendered correctly on screen but silently persisted the stale pre-change data — reload and the "successful" import or apply would quietly revert. Fixed by having `Store.save`/`persist` take the current state explicitly rather than trusting an internal copy, which makes the whole bug class impossible rather than patching the two call sites that happened to trigger it.
  - Also surfaced and fixed: "Swap this day" is offered on the rest-day screen itself, but swapping a rest day to a training template didn't actually un-rest it — the rest-day branch in `buildTodayViewModel` and `isDayCompliant` short-circuited regardless of any swap, so the swap silently did nothing. A swap now correctly promotes that day to a training day for the week, and compliance requires actually completing it rather than auto-passing.
- [x] **Full codebase evaluation, then the top-priority findings fixed** (code first, then workout logic, per request):
  - **Mid-typing focus loss** (deferred in the previous round) — typing into a set re-rendered the *entire* Today tab ~400ms later via a full `innerHTML` rebuild, stealing focus out from under whatever field you'd already moved to (and, on Android, closing the keyboard). Fixed with a targeted refresh path (`refreshTodayLite`/`patchExerciseCards`) that patches only what can actually change (checkmarks, a card's "complete" class, the day header tag, the day strip, top chips) in place, leaving the `<input>` elements themselves untouched. Full re-renders are still used everywhere else (tab/day/week changes, swaps, modals) — only the "typed into a set" path needed this.
  - **Tapping a set's checkmark recorded "1 rep"** (or "45 sec"), a placeholder that then became that session's worst set and skewed progression, PRs, and the trend chart. `renderExerciseCard` now stashes the exercise's actual suggested reps/weight on the card, and `toggleSet` fills that in instead.
  - **Streak-milestone bonuses aside, XP could be farmed** by clearing a completed exercise's set and refilling it — completion is a transient state, so it re-paid the same per-set/PR-bonus XP every time. Fixed with a permanent `_xpAwarded` flag per exercise-per-session (not the existing transient `_wasComplete`), seeded from `_wasComplete` for exercises completed before this fix so nothing already paid gets double-paid once.
  - **Import had no real safety net.** A confirm dialog existed, but any parseable JSON was accepted — picking an unrelated file (even a plan-changes export) got silently reinterpreted as an empty legacy backup and wiped everything, and a backup from a *newer* app version got silently "downgraded" instead of rejected. `validateImportPayload` now checks the file plausibly has TRAIN's shape and that its schema version isn't newer than this app understands, and a backup of the current state downloads automatically before anything is overwritten.
  - **"Longest streak" wasn't actually being persisted anywhere** — `computeStreakInfo` only ever *read* `state.longestStreak` (maxing it against the current streak for display); nothing ever wrote a new peak back once one occurred, so the very first missed day after a personal-best streak erased it from "Longest" forever. Added `computeLongestStreakEver` (a full day-by-day rescan from the earliest recorded activity) plus a `syncLongestStreak` call at every point the streak could have grown, including once on load to catch up any account whose peak predates this fix.
  - **Readiness was cosmetic** — the PUSH/STEADY/HOLD/RECOVERY verdict was computed and displayed but never affected anything. `suggestProgression` now suppresses any suggested increase (weight or reps) on a HOLD or RECOVERY day, and a RECOVERY banner on the Today screen nudges toward "Swap this day" to rest or light cardio. Submitting a readiness check-in now re-renders Today immediately (it previously only updated the readiness panel itself, so the effect wouldn't show until something else happened to trigger a render).
  - **Progression jumped straight to a 5%-ish weight bump on any hit**, regardless of home-gym reality (fixed dumbbell increments, no way to add 1.6 lb). Reworked into rep-range progression: each loaded exercise now has a floor (`targetReps`) and a ceiling (`targetRepsMax`, editable per-exercise in the template editor; defaults to floor+4), and a hit builds reps up through that range before weight moves at all. When weight does go up, it snaps to the next weight in a new Settings → **Dumbbells You Own** list instead of an arbitrary number — and once the heaviest owned weight is maxed out, it keeps progressing on reps past the nominal ceiling instead of stalling. No owned-weights list configured falls back to the old percentage bump, so the app still works with zero setup.
  - **PRs, plateaus, and the trend chart only ever looked at raw weight**, so 30lb×8 → 30lb×12 — real, meaningful progress — registered as *no change at all*, and could even trigger a false "plateaued" flag. All three now compare estimated one-rep max (Epley: `weight × (1 + reps/30)`) instead, computed from whichever single set in a session actually had the best 1RM (not the session's max weight and max reps independently mixed together, which could come from different sets). Catalog entries gained a `bestE1RM` field (schema v4, additive migration backfilling it by rescanning full session history, since it can't be reconstructed from the existing `bestWeight`/`bestReps` fields alone).
- [x] **Deload weeks + failure handling** — the last two "workout logic" gaps from the evaluation:
  - **Per-exercise failure handling.** Missing target used to just repeat the same weight forever. Each catalog entry now tracks `missStreak` (consecutive sessions in a row that missed target), computed once an exercise is actually complete for the session (not on every keystroke while still mid-entry, which would otherwise flicker the streak as the "worst set so far" changes). Two misses in a row and `suggestProgression` stops asking for the same failed weight a third time: it suggests dropping ~10% (loaded) or ~20% off the rep target (bodyweight/timed), resetting to the rep-range floor to rebuild from. The 10% weight cut snaps down to the nearest owned weight when one's configured (never landing on a plate that doesn't exist), always floored so it's a genuine step down rather than rounding back up near the original. Missing the deloaded weight too just deloads again from wherever it landed — self-correcting rather than a one-shot event. `missStreak` resets to 0 the moment a session actually hits.
  - **Deload weeks.** A new per-week toggle ("Deload This Week", on the Today tab below the week nav) backs off *every* exercise for that week — hit or miss, regardless of readiness or any single exercise's own history — since a real deload is a program-wide decision, not something to infer silently. The app nudges toward it (a banner + one-tap "Start Deload Week") once 2+ exercises have independently stalled (plateaued, or on their own 2+ miss streak) at the same time, since that pattern points more toward fatigue/life than any one exercise's programming. The AI digest got a matching "Deload status" section (current state, which exercises are struggling, and a recommendation when the same threshold is crossed) — deliberately a plain-language nudge rather than something the JSON plan-change import handles, since deload weeks aren't part of the templates/weekPlan schema that import already covers.
  - Custom exercises hit a real bug while building this: `suggestCustomProgression` builds its `lastPerf.reps` and its own target from the exact same catalog field (`catalogEntry.lastReps`), so the ordinary "did you hit floor" check is *always* true for them by construction — the miss-streak deload trigger would silently never fire for a custom exercise no matter how many times it missed. Fixed by trusting the catalog's own `missStreak` directly rather than re-deriving a hit/miss verdict from `lastPerf`, which also simplified the loaded-template-exercise path (the two checks were redundant there anyway, since `missStreak` only increments when a real miss already made `hitFloor` false).
  - Schema v5: `missStreak` added to catalog entries (backfilled at 0 — reconstructing a real streak from history isn't reliable, since it depends on whatever target was live in the template at the time, so this intentionally starts fresh rather than guessing) and `deloadWeeks` (a `weekStartKey -> true` map) added to top-level state.
- [x] **Attribute formulas fixed** — both used to measure the wrong thing:
  - **Strength was a straight PR count.** That spiked the moment you added any new exercise (a first-ever log always "beats" a baseline of zero, so adding exercises alone inflated the score with no actual strength change) and drifted toward zero for someone holding steady strength, since holding steady sets no new records. Replaced with `computeStrengthTrend`: the average % change in per-exercise performance (estimated 1RM for loaded, reps/seconds for bodyweight/timed) between your earliest and latest session of each exercise within the last 30 days, across every exercise with at least two sessions in that window — one data point isn't a trend, so a brand-new exercise no longer moves the score at all. The score centers on 50 for a flat trend (holding steady), rising or falling with the average direction; a fresh account (or one with no exercise logged twice in the window yet) shows 0, same zero-state convention as Consistency.
  - **Endurance was raw cardio minutes, no intensity signal.** A hard 30-minute interval session and an easy 30-minute walk-pace ride scored identically. Now weighted by `cardioEffortMultiplier`, a rough effort multiplier from each session's logged average HR relative to your own resting-HR baseline (already collected for the readiness check-in — no new field to fill in). A session with no HR logged still counts at a neutral 1x, identical to the old plain-minutes behavior, so nothing is penalized for skipping that optional field.
- [x] **PWA installability** — `app/manifest.json`, `app/service-worker.js` (cache-first with background revalidation for the app shell), and `app/icons/` (192/512/512-maskable/apple-touch-icon, generated as a simple accent-green "T" monogram) added alongside `index.html`, which links the manifest, sets theme-color for light/dark, and registers the service worker with a guard that skips itself entirely on `file://` (where nothing about this changes — the app still opens and works exactly as before, fully offline, as a bare local file). **Service workers cannot register on `file://` at all** — this is a hard browser restriction, not a bug to fix — so real installability ("Add to Home Screen" with a standalone window and offline caching) needs `app/` served over https or `localhost`; opening the file directly will never show an install option no matter what's in the manifest. GitHub Pages pointed at this repo is the natural free option given it's already hosted here, and keeps the "no server" principle intact (Pages serves static files only, no server-side code added). Deployed live via a `.github/workflows/deploy-pages.yml` Actions workflow (auto-redeploys on every push to `app/**`); the one part that couldn't be automated is that the *first-ever* Pages site on a repo has to be created by an authenticated owner (`Settings → Pages → Source → GitHub Actions`) — the workflow's own token is refused ("Resource not accessible by integration") from creating that first site, confirmed by three failed attempts before landing on this as the real, permanent constraint rather than a bug to keep chasing.
  - **Update banner.** An installed PWA's already-open tab doesn't swap in new code on its own — the service worker updates and activates itself (`skipWaiting()`/`clients.claim()`) but a page that's already loaded keeps running what it loaded until its next navigation. Added an in-app "Update available" banner instead of leaving that invisible: `registerServiceWorker` tracks whether the page was already under an existing service worker's control when it loaded (so the very first install never shows it, only a genuine later update does), listens for a new worker reaching `activated`, and also proactively checks for updates whenever the app returns to the foreground (`visibilitychange`) rather than waiting on the browser's own much slower periodic check — relevant since a workout app plausibly stays open/backgrounded for a while. The banner's Reload button just reloads (the new worker is already active and serving); a dismiss (✕) defers without forcing a reload. Verified against a real simulated deploy (not just reading the code) with Playwright: no false positive on an ordinary reload, banner appears when a real update lands while the app is open, Reload lands cleanly on the new version, dismiss hides it without navigating.
- [x] **Backup reminder + real auto-backup**, prompted by a real data-loss incident (a browser "clear site data" wiped IndexedDB/localStorage together, taking logged workouts with it — see the git history around the update-banner work):
  - **Reminder.** `Store.lastBackupAt()`/`markBackupNow()` track when a backup last happened (a plain localStorage timestamp, deliberately outside the synced state blob itself — backing up the backup timestamp inside the backup would be circular). Settings shows "Last backup: N days ago"; once real data exists (at least one session logged) and it's been 14+ days (or never), a dismissible top banner nudges toward Settings, snoozing itself for 24h on dismiss rather than reappearing on every render while still overdue.
  - **Auto-backup to a linked file.** Settings → "Auto-Backup to a File" lets you pick an on-disk file once (File System Access API, Chromium-only — feature-detected, hidden everywhere else) that TRAIN then keeps rewritten with a fresh export automatically: `Store` debounces a write 4s after each save (collapsing a burst of ordinary saves into one disk write) and flushes immediately when the app backgrounds (`visibilitychange` → hidden), which is the best chance to catch state before a session actually closes. Manual Export/Import is untouched and still works everywhere this doesn't.

Span conventions applied: uppercase letter-spaced Barlow section labels, Barlow for headlines and big numbers, uppercase letter-spaced buttons with one primary color, Span status badges for readiness, Span toast/modal surfaces, the amber CRT power-on wordmark (played once per load, holding a static glow rather than Span's looping pulse, since the header is in view all workout). Semantics follow Span too: the accent marks what's active right now, green (Span's success) marks done — completed sets and exercises, logged days — and warnings share the accent. Deliberate departures for a phone used mid-workout: 44px tap targets and 15px inputs instead of Span's desktop density, and the modal stays a bottom sheet. Inter (variable) + Barlow 600/700/800 are embedded as woff2 data URIs (~117KB, SIL OFL; licenses in `app/fonts/`) instead of Span's Google Fonts link, keeping the single-file, no-network-calls principle. App icons and manifest colors now use Span's amber on its dark background.

- [x] **Share links.** Settings → Data → Share My Plan builds `…/index.html#plan=<token>`: the workouts (non-empty, non-cardio), weekly plan, rest days, and bank categories of the exercises in them — never history, readiness, or anything else personal — as plan-change JSON, deflate-compressed via `CompressionStream` and base64url-encoded (~900 characters for a full plan). Uses the Android share sheet where available, else Copy Link. Opening a link (or pasting one — alone or inside a whole message — into Import Plan Changes, which is also the route for an iPhone Home Screen app, since links open in Safari's separate storage) decodes it into the same preview-then-Apply step; the fragment is cleared from the address bar so a reload doesn't reopen it. Because plans can now come from other people, plan import treats its input as untrusted: names/labels are length-capped, sets/reps clamped, object-internal names (`__proto__` etc.) refused as exercise names, and link tokens size-capped before decompression.
- [x] **Storage protection.** Browsers keep site data as "best-effort" by default and may clear it under disk pressure, installed or not. Once there's real data, the app calls `navigator.storage.persist()` (Chrome grants or refuses silently — installed/regularly-used apps usually get it; Firefox asks). Settings → Data shows whether storage is protected, current usage, a Protect Storage button, and — in an iPhone Safari tab — a note to add TRAIN to the Home Screen, since Safari clears website data after 7 days without a visit but exempts Home Screen apps. Backups remain the real safety net.
- [x] **Releases come from `main` only.** Deploys run from `main` and are gated on the test harness passing; `test.yml` runs the harness on every other branch and every PR. See README → Releases.

- [x] **First-run intro + six presets.** A brand-new install (schema v8 `onboarded: false`; every migrated account is marked done, so existing users never see it) opens a short intro: *Find Me a Plan* or *I'll set it up myself*. The questions: goal, days/week, session length, equipment (plus dumbbell weights owned, which feed progression), experience, any health considerations (pregnant/postpartum, injury/surgery, medical condition, pain — asked neutrally of everyone, no sex question), and areas to go easy on (knees, shoulders, lower back, wrists). `recommendPresets` ranks all six presets (Five-Day Hybrid, Foundations, Upper/Lower, Bodyweight Only, 20-Minute Express, Low-Impact/Joint-Friendly); `tailorPlan` adjusts the chosen one using an `EXERCISE_TRAITS` table (equipment needed, areas stressed, impact, lying-on-back, crunch-style, and ordered alternatives): conflicting exercises are swapped for the first fitting alternative or left out, weighted moves that work unweighted go unweighted without dumbbells, 20/30-minute answers cap exercises and sets (keeping the core exercise), and "new" trims a set. Every adjustment is listed in the preview before Apply. Any health consideration shows a see-your-doctor/midwife/physio note, leaves out jumping and leads with the joint-friendly plan; pregnant/postpartum also leaves out lying-on-back and crunch-style work. On a fresh install, plan import's new `removeTemplates` clears the untouched default workouts the chosen plan doesn't use. Share-link recipients skip the intro (the shared plan is their start). Settings → Weekly Plan → *Find a Plan…* reruns it later with saved answers. 15 alternative exercises were added to the built-in bank. The harness sweeps every preset × 300 answer combinations to confirm no conflicting exercise ever survives tailoring. **Presets are general fitness programming and need review by a qualified trainer/physio before sharing widely — see the preset evaluation.**

- [x] **Attributes became a six-spoke radar.** Strength, Endurance and Consistency were bars; they're now spokes of a hexagonal radar alongside three new, data-derived scores: **Core** (days with core work in the last 30 vs a 5-a-week goal), **Balance** (the lightest of push/pull/legs sets against the heaviest over 30 days — 99 = even; waits for 12+ sets before scoring) and **Recovery** (average readiness verdict over the last 14 days: PUSH 99, STEADY 70, HOLD 40, RECOVERY 15 — context, not a grade). A dashed outline shows the same six scores as the account stood 30 days ago (`stateAsOf` removes later sessions and check-ins, since the underlying score functions only bound their windows from below), drawn only once there's history that old. A card under it explains one spoke — the weakest by default ("Focus area"), or whichever spoke was tapped — with its change vs 30 days ago. Hand-drawn SVG on the theme tokens, so it follows all four themes. The AI digest reports all six.
